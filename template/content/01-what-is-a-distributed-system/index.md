## 先建立一个直觉

一台机器扛不住的时候，最自然的想法是：多找几台机器一起干。

于是原本「一个进程读自己的内存」的简单世界，变成了「一堆进程通过网络互相发消息」的世界。[[term:distributed-system]] 描述的就是后者。

麻烦也随之而来。网络会丢包，机器会宕机，消息会乱序 —— 而且你**没有全局时钟**可以依靠。分布式系统的绝大部分难度，都源自这三件事。

## 三个绕不开的概念

### 节点

[[term:node]] 是集群里的一台机器，或者一个独立进程。节点之间只能靠收发消息通信，谁也不知道对方的真实状态 —— 这就是为什么「探测对方是否还活着」本身就是一个难题。

### 副本

[[term:replication]] 指的是把同一份数据放在多个节点上。好处很直接：任何一个节点挂掉，数据还在别处。代价同样直接：写一份数据要写多处，它们之间可能暂时不一致。

### 共识

[[term:consensus]] 是让多个节点对同一件事达成一致的过程。它是 [[term:replication]] 能够正确工作的前提 —— 如果节点们对「当前谁是主」都意见不一，副本就无从谈起。

达成共识的方式之一，是选出唯一的协调者，这就是 [[term:leader-election]]。

## 一个最小例子

设想我们要把一条数据写进三个节点。最朴素的写法是逐个发送，然后等待多数派确认：

```python
def replicate(key, value, replicas):
    """把一条键值对写进所有副本，返回是否得到多数派确认。"""
    acks = 0
    for node in replicas:
        # 注意：这里的 send 可能失败，也可能永远不返回
        if send(node, ("put", key, value)):
            acks += 1
    return acks > len(replicas) // 2
```

这段代码故意留了两个洞，值得停下来想一想：

- `send` 失败怎么办？重试多少次算够？
- 如果 `send` 成功了，但对方其实没写进去，多数派确认还有意义吗？

这两个洞，正是后面所有分布式协议要填的东西。

## 常见误解

| 误解 | 实际情况 |
| --- | --- |
| 加机器就能提升性能 | 协调开销可能让整体更慢 |
| 网络是可靠的 | 丢包、延迟、分区都是常态 |
| 存在全局时钟 | 只有各机器自己的时钟，而且会漂移 |
| 副本越多越安全 | 副本越多，保持一致的成本越高 |

而 [[term:fault-tolerance]] 不是「不出故障」，而是**出了故障还能继续正确工作**。这个区别很重要：前者做不到，后者才是工程目标。

## 下一步

如果你能接受「网络不可靠、时钟不可信、节点会挂」这三条前提，就已经准备好进入真正的分布式共识算法了。
