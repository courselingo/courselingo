# 写作规范 · Writing Style

> 这份规范的存在理由只有一个：**让基础薄弱的中文读者能跟着思路走完，而不是读一堆正确的废话。**
> 凡是能机检的条目，都由 `scripts/check_style.py` 实际拦截。

## 1. 目标读者

一个**学过一门编程语言、但没接触过分布式系统**的中文读者。
他可能：
- 不知道「副本」「日志」「多数派」是什么意思（第一次出现要给一句白话）
- 会怀疑「为什么要这么麻烦」（要先把痛点讲出来，再给方案）
- 英文一般，看到大段英文会跳过（术语中英并给，但**解释用中文**）

## 2. 每篇的「脉络」——结构硬约束

读者必须能回答：**现状是什么 → 问题在哪 → 思路是什么 → 怎么做到 → 效果与代价是什么**。

因此每篇按这个顺序组织，标题可以自由起，但**这六段内容必须在**：

| # | 段落职责 | 读者读完应能回答 |
| --- | --- | --- |
| 1 | **现状与痛点** —— 不这么做会怎样 | 「为什么要费这个劲？」 |
| 2 | **直觉做法为什么不行** | 「那我想的那个办法错在哪？」 |
| 3 | **核心思路** —— 一句话说清 | 「它的主张是什么？」 |
| 4 | **机制怎么运转** | 「具体怎么做到的？」 |
| 5 | **代价与边界** —— 换来了什么、放弃了什么 | 「它不适用于什么情况？」 |
| 6 | **脉络回顾** —— 接回全课 | 「这一讲在整门课的位置？」 |

第 1 段与第 6 段是**硬性要求**，`check_style.py` 会检查锚点标题是否存在。

## 3. 反「AI 味」清单

AI 味不是文风偏好问题 —— 它是**信息密度低的信号**：句子在铺陈而不在推进。
下面每条都可机检，阈值是硬性的。

### 3.1 硬拦（出现即失败）

| 类别 | 具体 |
| --- | --- |
| 空洞总起 | 在当今、随着…的不断发展、众所周知、不难发现、显而易见 |
| 空洞收尾 | 综上所述、总而言之、总的来说、希望本文、让我们一起 |
| 营销腔 | 深入浅出、一探究竟、揭秘、全景、硬核、干货、赋能、抓手、闭环、维度、生态、范式、底层逻辑 |
| 机械分段 | 段首「首先，」「其次，」「再次，」「最后，」作为**唯一**的组织手段 |
| 空转铺垫 | 本文将带你、接下来我们将、下面让我们、值得一提的是 |
| 正文 emoji | 除图表标注外，正文不得出现 emoji |

### 3.2 限用（超阈值即失败）

| 项 | 阈值 | 为什么 |
| --- | --- | --- |
| 破折号 `——` | ≤ 1 处 / 1000 汉字 | 中文里连用破折号是最典型的 AI 腔 |
| 加粗 `**…**` | ≤ 1 处 / 250 汉字，且不得整段加粗 | 加粗过多 = 没有重点 |
| 「不是…而是…」 | ≤ 2 处 / 篇 | 这个句式被用滥了 |
| 设问（「为什么…？」「那…呢？」） | ≤ 4 处 / 篇 | 少量好，堆砌就是表演 |
| 每段行数 | ≤ 8 行 | 超长段落劝退初学者 |
| 小标题下的正文长度 | ≥ 3 行 | 只有标题没有内容 = 大纲不是文章 |

### 3.3 好写法 vs 坏写法

```
❌ 值得注意的是，在当今分布式系统的发展中，一致性是一个非常重要的维度。
   我们不仅要考虑可用性，更要考虑性能，让我们一起来深入浅出地探索这个硬核话题。

✅ 三台机器存同一份数据，网络一断，它们就可能各自为政。
   你只有两个选择：要么拒绝服务，要么让它们暂时不一致。没有第三条路。
```

差别不在文采，在于：**坏写法没有信息**。「非常重要」「深入探索」都可以删掉而不损失任何东西。

## 4. 具体优先

| 不要 | 要 |
| --- | --- |
| 「性能很好」 | 「实测 2.4 秒」/「论文报的数字是 X」 |
| 「可能出错」 | 「机器在第 3 步崩了，客户端只看到超时」 |
| 「使用某种协议」 | 「用两阶段提交：先 prepare，全票通过再 commit」 |
| 「很多系统都这么做」 | 点名：「GFS、HDFS、Ceph 都这样」 |

**没有具体数字时，就说清机制。** 宁可讲透一个具体场景，也不要罗列五个抽象名词。

## 5. 诚实优先

这是本项目的底线，也是反 AI 味的关键 —— AI 写作最难改的毛病是**不懂也敢写**：

- 论文/课程没说的，写「**论文没写**」，不要补一段听起来合理的推测
- 自己不确定的，写「**我们不确定**」，不要用模糊措辞掩盖
- 有争议的，把两方说法都摆出来，不要选一个当定论
- 引用了数字，标明来源

## 6. 面向初学者

- 术语第一次出现：`[[term:key]]` 标记 + 一句白话解释。例：
  「[[term:quorum]]指的是**多数派**：5 台机器里至少 3 台同意，就算通过。」
- 不要用「显然」「容易看出」—— 对初学者什么都不显然
- 抽象概念先给**具体场景**（三台机器、一份数据、一次断网），再谈一般化
- 需要读者回忆前文时，明确写「第 2 讲讲过…」，别指望他自己串起来

## 7. 配图

见 [figure-spec.md](./figure-spec.md)。要点：
- 每篇 **≥3 幅**，放在概念第一次讲不清的地方
- 图前一句引出、图后一句解读，图不能孤零零挂着
- `alt` 要能替代图片传达信息

## 8. 提交前自检

```bash
python scripts/check_style.py --root . --strict    # 文风机检
python scripts/validate.py                          # 授权与术语闸门
python scripts/check_figures.py --strict            # 配图房规
```
