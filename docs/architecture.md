# 架构设计 · Architecture

> 状态：Phase 0 草案。尚未实现，欢迎挑战。

## ⚠️ 前置于一切技术决策的约束：授权闸门

架构必须建立在一条法律结论之上 —— **翻译完整逐字稿或字幕属于衍生作品，复制了原作的全部表达**，其合法性完全取决于各课程的实际许可条款，而**这些条款目前一门都未核实**（见 [licensing-research-log.md](./licensing-research-log.md)）。

因此架构的默认产出被定为 **「原创讲解」而非「翻译逐字稿」**：

| 产出形态 | 架构地位 |
| --- | --- |
| 自己撰写的概念讲解、推导、代码注释 | ✅ **默认产出** —— 概念不受著作权保护，风险最低 |
| 术语表、学习路径、中英对照的**我们自己**的表述 | ✅ 默认产出 |
| 完整讲座逐字稿翻译 | ⛔ **默认关闭** —— 须先取得该课程的书面授权才可开启 |
| 视频字幕翻译 | ⛔ 默认关闭 |
| 官方作业答案翻译 | ⛔ 永久排除 |

这个约束不是「以后再优化」的合规尾巴，而是**决定产品形态的设计前提** —— 它也是「术语表前置、讲解为主」这套流水线的成因。

## 设计目标

1. **讲懂优先** —— 产出的是「中文讲解」，不是逐句替换的字幕。
2. **术语强一致** —— 术语在翻译**之前**确定，而非翻译之后修补。
3. **内容与工具分离** —— 流水线代码可复用；课程内容独立成仓，可单独授权、单独下线。
4. **可溯源** —— 每段产出都能回到原文位置。
5. **可校验** —— 机器能自动查出术语冲突与漏译。

## 流水线

```
原始材料（官方公开页 / 视频字幕）
      │  ① 采集：仅取结构信息与时间轴，原始材料不入库
      ▼
   分段切分（Lecture → 小节 → 句段，保留时间轴与层级）
      │
      ▼
   ② 术语抽取 ──► 课程术语表（人工确认后冻结）★ 关键闸门
      │
      ▼
   ③ 翻译（LLM + 术语约束注入 + 上下文窗口）
      │
      ▼
   ④ 讲解生成（概念前置 / 推导补全 / 代码注释）
      │
      ▼
   ⑤ 质量校验（术语一致率 / 回译抽检 / LLM 评审 / 人工复核）
      │
      ▼
   ⑥ 渲染发布（中英对照 Markdown → 静态站点）
```

## 关键决策

### 术语表前置（②）是最重要的一环

机翻翻车的根本原因不是模型不够强，而是**同一个词在不同段落被译成不同中文**。因此流程上把术语抽取提到翻译之前，并作为**人工闸门**：术语表未冻结，不开始翻译。

术语表是项目的核心资产，独立于模型 —— 换模型不应导致术语漂移。

### 中间格式统一为 JSON

每个句段是一条记录，携带：原文引用位置、译文、术语命中、生成方式、复核状态。

好处：翻译、讲解、校验、渲染四个环节解耦，任一环节可替换；也便于做质量统计。

```jsonc
{
  "id": "6.824-lec03-p012",
  "source": { "lecture": 3, "timestamp": "00:12:30", "url": "..." },
  "en": "...",
  "zh": "...",
  "terms": ["raft", "leader election"],
  "status": "machine" // machine | reviewed | approved
}
```

### 不存储原始材料

流水线只在运行时读取官方页面/字幕，**不把英文原文、课件 PDF、视频文件写进仓库**。

这既是授权上的安全设计，也避免了仓库体积膨胀。

## 未解决的问题

- **长上下文 vs 分段**：整讲一次投喂上下文更连贯，但成本与质量如何权衡？
- **讲解的边界**：讲多深算「讲懂」而不算「重写课程」？需要样例定标。
- **术语冲突消解**：同一英文词在不同课程中译法不同（如 `thread`），是否允许课程级覆盖？倾向：允许，且必须显式声明。
- **评测集**：人工复核成本高，如何构造小而有效的自动评估集？
