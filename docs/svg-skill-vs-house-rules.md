# 通用绘图技能 vs 本仓房规：对照与裁决

> 背景：技能目录中途出现两个通用绘图技能（`svg-diagram`、`archify`）。
> `cs168-author` 第一个发现并**没有自行采用**，而是把决定权交回 Lead
> （它的理由：「本课有冻结的 `docs/figure-spec.md` + `svg-lint --strict` 闸门，
> 通用技能的建议可能与本课房规冲突」）。**这个处理是对的。**
>
> 本文件是 Lead 的裁决。**裁决日期：2026-09-29。**

## 结论（先说）

> **不替换房规，不引入 `archify`，把 `svg-diagram` 作为**参考读物**下发给图作者，
> 并采纳它带来的**一条技术手法**（`<g transform>` 整体位移）与**一条判据确认**（标题按内容中心对齐）。**

**理由**：384 张图已经按房规产出，且房规是**机检项**（`check_figures --strict`、`svg-lint --strict`、`layout_check`）。
**换标准 = 让已过闸门的 384 张图变成「按旧标准合格、按新标准未知」** —— 那是净损失。
**而通用技能里对本项目**新增**的东西只有一条（见下），其余都是房规已有的，只是说法不同。**

## 逐条对照（我实测的）

| `svg-diagram` 的规则 | 本仓房规/实际做法 | 关系 |
| --- | --- | --- |
| 相邻块间距 ≥25px，推荐 25–30px | 复核者按「**25–30 规范**」判（`eth-author` 第 1 讲原文） | **一致** |
| 箭头两端留白 5px / 终点 = 目标边 − 11px（5 清位 + 6 头部） | 本仓有「**5/11 箭头补偿**」（`figgen` 的做法） | **一致** |
| 单行框高 = 字号 × 3；两行 = 36 + 行高 | `mit6006-author` 实测：`box()` 给 3 行 fs=12 ⇒ **36 + 2×18 = 72** | **一致（同一公式，一边是文档、一边是实测撞出来的）** |
| 框内文字垂直居中：`y = 框中心 + 字号 × 0.35` | `figgen.py` 当初为解决同一问题而写成构造式 | **一致** |
| 标题按**内容中心**对齐，不是 viewBox 中心 | `eth-ca` 第 1 讲那条争议：复核者算「中心 x≈782 / 图身 716」；作者实测 `content L=150 R=630 ⇒ centre=390`，`title x=390` | **一致 ⇒ 作者是对的** |
| CJK 字体栈必须保留 `Noto Sans CJK SC`（Linux 服务端渲染） | 本仓在 Linux CI 上构建 | **一致（且这是重要的一条，房规里也应有）** |
| XML 特殊字符必须转义（`&` `&lt;` …） | **实测 958 张 SVG：解析失败 0、裸露 `&` 0** | **无缺口** |
| `<g transform="translate(dx,0)">` 整体位移修正不对称留白 | **房规里没有这个手法** | ★ **新增，值得采纳** |
| `archify`：输出**独立 HTML**、内联 SVG、明暗主题、可导出 | 本仓要的是 **`.svg` 文件 + Markdown 引用**（MkDocs 构建） | **不适用** |

## 裁决细节

### ① 采纳：`<g transform="translate(dx,0)">`

**它解决的是本会话反复出现的一类复核意见**：「整幅图不居中／左右外边距不对称」。

**实例（都是同一类）**：
```
cs168  arch-2       「底注未与标题及页面水平居中对齐，约偏右 40–50 像素」
cs168  headers-1    「左右外边距 48 vs 104，整幅图水平方向不对称、不居中」
cs168  sharing-5    「整排流程块左边距小、右边距大，中心线略偏左」
eth-ca -3           「标题偏右约 60px」（作者实测否证，但同类）
```

**而通用技能给的手法比我此前的建议便宜得多**：
> 把内容整体包进 `<g transform="translate(dx, 0)">`，`dx = (右边距 − 左边距) / 2` ——
> **不必逐个改坐标。**

**⇒ 而它自己也说了代价**（这一条我认）：
> 「坐标不再等于渲染位置，后续编辑要心算减掉那个偏移 ——
> **若后面还有大改，就把偏移折进各个坐标并去掉 `<g>`。**」

**⇒ 下发时的口径**：**只用于「已经定稿、只差居中」的图；不要用它掩盖布局问题。**

### ② 确认：标题按**内容中心**对齐

**这条把 `eth-ca` 第 1 讲那处争议定了案。**
复核者主张「标题应居中」时算的是**拼版/画布中心**（x≈782、716，而那张图 viewBox 宽只有 707）；
作者实测的是**内容中心**（`content L=150 R=630 ⇒ 390`，`title x=390`，房规 `title-not-centered` **0 warning**）。

**⇒ 通用技能明确写**：「**Center the title on the *content* center, not the viewBox center**（they differ whenever the content is asymmetric）」
**⇒ 所以作者是对的，而复核者的 px 值是坐标系用错了。**

**★ 但由此产出一条**给复核者的要求**（已并入 `附录十一`，此处重申）：**
> **报 px 必须带坐标系（图坐标 / 拼版坐标），并说明基准是内容中心还是画布中心。**

### ③ 不引入 `archify`

**它产出独立 HTML**（可探索、有明暗主题、可导出）。**本项目的图是 MkDocs 里的静态 `.svg`**，
**且 384 张图共用一套房规与指纹去重机制**（「版面指纹互不相同」是机检项）。
**⇒ 它的能力（交互、导出）对本项目是要解决的问题的**另一面**，不是这一面。**

### ④ 不下发给全部作者

**下发给「正在画新图的人」**（`cs168-author`、`eth-author` 的接手者、`mit6006-author`、`mlsys-author`），
**并且明确说：房规优先，冲突时以 `figure-spec.md` + 机检为准。**

**★ 而更重要的不是这个技能本身，是它**验证了房规**：**
> 房规里那些「实测撞出来的数」（5/11 补偿、36+2×18、0.35 基线偏移、25–30 间距）
> **在一份独立的通用规范里全都有，且数值相同。**
> **⇒ 这说明那套房规不是我们拍脑袋定的，而是这类图的一般规律。**

**★ 反过来**：`svg-diagram` 有一条我们要抄的（`<g transform>`），
而我们有一条它没有的 —— **「版面指纹互不相同」**（防止两张图撞版面）。
**⇒ 两边各有所长，而这次交换是净收益。**
